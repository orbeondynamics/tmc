# 0. Propósito y alcance del repositorio maestro

Este documento consolida, en una sola referencia, la información
disponible sobre el proyecto TMC World / TMC website que aparece en los
documentos del proyecto y en el contexto recuperable de las
conversaciones. Su finalidad es que el proyecto pueda continuar en otro
chat o con otra IA sin depender de reconstruir decisiones desde cero.

La consolidación conserva decisiones, requisitos, cambios, activos,
nombres, rutas, controles, criterios de aceptación, pendientes y
correcciones ya discutidas. Cuando una decisión posterior sustituyó una
recomendación anterior, se conserva la decisión vigente y se documenta
el cambio para evitar que una IA vuelva a aplicar una versión obsoleta.

Este documento debe tratarse como repositorio de continuidad del
proyecto. No sustituye los archivos fuente ni el repositorio de código;
los complementa y registra el estado conocido.

# 6. Sistema de cámara e interacción

-   PerspectiveCamera.

-   Sin OrbitControls.

-   Cámara controlada por código.

-   Intro: cámara guiada por timeline.

-   Después de la intro: cámara guiada por scroll.

-   Trayectoria mediante CatmullRomCurve3 atravesando hero y cuatro
    hotspots.

-   Curva de target/orientación separada de la trayectoria de posición.

-   Damping para suavizar el input de scroll.

-   Scroll y navegación directa deben converger en el mismo pose de
    cámara para cada área.

-   Hotspots: marcadores 3D proyectados y clicables.

-   Una sola referencia de progreso compartida; evitar que GSAP y R3F
    tengan relojes independientes.

## 6.1. Scroll

-   GSAP + ScrollTrigger + Lenis son el sistema aprobado.

-   Lenis está instalado y comiteado en Fase 0; debe verificarse contra `package.json` y el estado de Git cuando corresponda.

-   \@gsap/react está instalado y comiteado en Fase 0; debe verificarse contra `package.json` y el estado de Git cuando corresponda.

-   scroll-world NO se usa.

-   TMC World es un mundo 3D vivo, no un vídeo pre-renderizado.

-   No usar window.scrollY de forma independiente en GSAP y R3F; ambos
    deben consumir el mismo estado/progreso.

# 10. Performance, responsive y accesibilidad

-   Meta oficial de carga inicial: \<3--4 MB antes de interacción.

-   Optimización KTX2/Draco aprobada para fase posterior, no como
    bloqueo inicial.

-   Conservar originales y preparar sustitución por archivos optimizados
    sin cambiar la lógica.

-   InstancedMesh para elementos repetitivos del skyline.

-   HDRI/baked lighting cuando sea posible.

-   frameloop=\'demand\' + invalidate cuando corresponda.

-   Controlar peso de GLB, texturas y HDRI.

-   Calidad automática según capacidad del dispositivo/GPU.

-   No habrá toggle manual visible inicialmente.

-   Detectar capacidad mediante señales de hardware/pointer y no
    user-agent sniffing.

-   En hardware limitado: reducir shader, geometría y DPR; mantener el
    mismo mundo.

-   Fallback HTML semántico si WebGL no está disponible.

-   Fallback mediante imágenes/stills y navegación estándar.

-   prefers-reduced-motion soportado.

-   Desktop/tablet/mobile con la misma arquitectura.

-   Mobile adapta composición, hotspots y calidad sin crear otra
    experiencia conceptual.

# 12. TMC Logo 3D --- estado, especificación y prompt operativo

El logo 3D es un asset crítico. Se han realizado varias iteraciones en
Claude y el principal problema detectado fue que el grosor visual no
cambiaba suficientemente. Por eso se estableció un control numérico
interactivo como requisito obligatorio.

## 12.1. Asset fuente

-   GLB fuente conocido: tmc-world-logo-2d.glb; también existe una
    variante posterior cargada como tmc-world-logo-2d(1).glb.

-   El GLB fuente puede estar negro; la implementación final debe
    convertirlo a dorado.

-   El asset fuente debe conservarse y quedar reemplazable.

-   No generar un nuevo GLB salvo necesidad técnica real.

## 12.2. Configuración aprobada

  -----------------------------------------------------------------------
  **GOLD_COLOR**                      0xC9A24B
  ----------------------------------- -----------------------------------
  **LOGO_SIZE**                       545 / targetWidth 545 o equivalente

  **LOGO_THICKNESS**                  2.0 inicial; editable

  **LOGO_ROTATION**                   Mantener comportamiento actual;
                                      convertir en variable

  **LOGO_ROTATION_SPEED**             Mantener comportamiento actual;
                                      convertir en variable

  **RING_OUTER**                      340

  **RING_INNER**                      300

  **Círculo**                         Objeto independiente; no modificar

  **Escala**                          Desacoplada de la geometría del
                                      GLB; controlada desde Three.js
                                      mediante scale/targetWidth

  **Posición**                        Mantener X/Y/Z y orientación
                                      inicial

  **Grosor**                          Modificar profundidad 3D sin
                                      deformar X/Y ni silueta frontal
  -----------------------------------------------------------------------

## 12.3. Control interactivo de grosor

-   Debe existir un campo numérico THICKNESS visible junto a SIZE,
    ROTATION y ROTATION SPEED.

-   Valor inicial: 2.0.

-   Debe aceptar valores como 1.0, 1.5, 2.0, 2.5, 3.0, 4.0, 5.0.

-   El cambio debe verse en tiempo real sin recargar.

-   THICKNESS no puede ser simplemente scale uniforme.

-   Prueba obligatoria: 1.0 debe verse más delgado, 2.0 grueso, 3.0 más
    grueso que 2.0.

-   Si el cambio numérico existe pero el volumen visual apenas cambia,
    no se considera terminado.

## 12.4. Método de volumen

-   Si el GLB no permite modificar directamente su profundidad,
    implementar la solución 3D más limpia posible con Three.js/geometría
    auxiliar.

-   Prioridad: volumen físico real + silueta frontal intacta.

-   No deformar ancho, alto, proporciones o forma corporativa.

-   No usar cámara o iluminación para fingir volumen.

-   No modificar el círculo para acomodar un error de escala.

-   No añadir dependencias innecesarias.

# 25. Historial de decisiones y aprendizajes del proyecto

-   El proyecto evolucionó desde un website conceptual basado en el TMC
    Concept hacia TMC World: una experiencia 3D viva.

-   Se descartó convertir toda la imagen de Miami en 3D porque agregaría
    complejidad/peso sin aportar necesariamente una mejor experiencia.

-   Se estableció que los 10 assets son piezas independientes
    técnicamente pero deben percibirse como una única escena.

-   Se descartó utilizar scroll-world porque su pipeline está pensado
    para vídeo pre-renderizado y manipula video.currentTime; TMC World
    necesita una escena R3F viva.

-   Se decidió que las cuatro capacidades son destinos espaciales y el
    menú corporativo es una capa informativa separada.

-   Se decidió que el pequeño logo TMC de arriba a la izquierda
    sustituye un house icon y funciona como Home.

-   Se decidió que el footer debía dividirse en cuatro bloques concretos
    y no en un footer genérico.

-   Se decidió que el indicador de ruta activa debía ser sutil.

-   Se decidió que la persona debía ser fotorealista y preservada según
    el Master Miami.

-   Se decidió que los hotspots debían ser 3D proyectados y clicables.

-   Se decidió que Skip Intro debía ser discreto abajo a la derecha y
    recordar la sesión.

-   Se decidió que calidad sería automática, sin toggle manual inicial.

-   Se decidió que KTX2/Draco se optimizaría después y que los
    originales debían conservarse.

-   Se fijó un presupuesto de carga inicial de \<3--4 MB antes de
    interacción.

-   Se aprobó JSON-LD para TMC y las cuatro líneas.

-   Se detectó una inconsistencia recurrente en iteraciones del logo:
    Claude reportaba aumento de grosor pero el resultado visual seguía
    pareciendo casi igual. La corrección fue exigir un control numérico
    THICKNESS y probar 1.0/2.0/3.0 visualmente.

-   Se aclaró que LOGO_THICKNESS = 2.0 es un valor inicial de prueba y
    no una interpretación matemática de \'dos veces 1.35\'.

-   El logo debe ser físicamente grueso sin deformar X/Y y sin utilizar
    la cámara o iluminación para fingir volumen.

-   El archivo entregado por una IA debe ser el mismo archivo modificado
    cuando se trabaje sobre una implementación existente; no deben
    crearse versiones paralelas salvo necesidad explícita.

-   Para nuevos archivos del proyecto se debe usar nomenclatura sin
    espacios, preferentemente con underscores.
